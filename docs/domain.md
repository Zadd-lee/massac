## 1. 한 문장 정의 [확정]

여러 시스템에 흩어져 있던 정부지원 교육사업의 신청·일정·강사·교구·서류 데이터를 하나의 교육 단위로 모으고, 일정·학생 수 같은 변경이 연관 업무에 주는 영향을 추적해 운영 누락을 막는 시스템.

핵심 4영역: 교육 Workflow / 제한 자원 스케줄링 / 변경 영향 관리 / 운영 Task 관리

운영 철학: 시스템이 계산할 수 있는 것은 시스템이 처리하고, 사람이 판단해야 하는 예외만 운영자에게 전달한다 (Human-in-the-loop).

기존 도구: LMS, 운영 Google Sheet, 강사·교구·간식 업체 Sheet, Google Form, Google Drive, KakaoTalk, 전화.

## 3. 신청

### 3.1 신청 출처 [확정]
사전 수요조사, 사전 신청, LMS, 전화, 운영자 직접 등록, 강사 연계. 사전 신청 Form은 여러 종류가 생길 수 있다.

[확정] 기수(cohort)는 EducationRequest에만 둔다. [가설] `ApplicationSource`(예: "2026년 1차 사전수요조사")를 엔티티로 두고, 그 안에 `ApplicationSourceType` enum(PRE_APPLICATION, LMS, PHONE, OPERATOR, INSTRUCTOR_CONTACT)을 둔다. 출처를 enum 하나로 고정하지 않는다.

### 3.2 EducationRequest와 EducationClass [확정: 분리]
- EducationRequest: 처음 요청한 수요 (희망 교육일, 학생 수, 프로그램, 출처, 교사 직접강의 여부). 최초 값은 바뀌지 않게 보존한다.
- EducationClass: 일정 협의와 자원 검토 후 운영하기로 확정된 교육.
- [확정] 하나의 EducationClass는 여러 날짜에 걸쳐 진행되고, 하루에 여러 차시가 있을 수 있다. 1차시 = 1교시. `EducationClass 1 : N EducationSession`(날짜, 시작 시간).
- [확정] 하루 최대 차시 수는 학교급(초·중·고)에 따라 다르며 관리자 설정값이다.
- [확정] EducationClass는 항상 한 학교, 학생 수는 교육 전체에 하나다.
- [확정] 학교 주소는 하나지만 교육마다 상세주소(예: 4층 누리반, 1층 교무실)가 달라진다 → 교육별 배송지·교육 장소 상세 스냅샷.
- [가설] Request : Class = 1 : N 을 허용하는 구조로 둔다. 하나의 신청이 여러 Class로 나뉜 사례가 있는지는 [미정]이지만, 1:N 허용 비용이 낮다.
- [가설] 중복 신청은 운영자 판단 후 `duplicateOf`로 원래 Request를 가리킨다 (자동 병합 안 함).
- [가설] 신청 당시 학교명·담당자 연락처는 Request에 스냅샷으로 저장한다. 사용자의 현재 소속과 다를 수 있다.

### 3.3 기수 [확정]
기수는 기간 단위다 (예: 2026년 1기). 관리자가 추가할 수 있어야 한다.
[가설] `Cohort`(이름, 시작일, 종료일) 엔티티. EducationRequest와 EducationClass가 Cohort에 속한다.

### 3.4 LMS 연동 [확정: API 없음]
LMS → 주기적 수집 → Import → EducationRequest. 같은 데이터를 반복 수집해도 Request가 중복 생성되면 안 된다.
- [가설] `(source, externalId)` 유니크로 멱등 처리.
- [가설] 도메인은 크롤링에 의존하지 않도록 `RequestImportPort` 같은 포트를 두고, 어댑터를 교체 가능하게 한다. MVP1은 운영자 직접 입력만, CSV·크롤링 어댑터는 MVP2.
- 사전신청과 LMS 신청이 같은 교육인지는 멱등성과 별개 문제다. 판별 기준은 [미정].

## 4. 우선순위와 실행 가능성

### 4.1 우선순위 규칙 [확정]
1. 사전 수요 / 사전 신청
2. 강사가 직접 연결한 학교
3. LMS 일반 신청

LMS 안에서 고려: 연속 교육 여부, 교사 직접강의, 기존 협력 관계, 신청자 협조, 학생 수, 사업상 특별 조건.
최종 처리 여부와 순서는 운영자가 결정한다. 시스템 우선순위는 의사결정 지원이다.

### 4.2 모델링 [가설]
가중치 점수 합산은 1~3 순서를 뒤집을 수 있으므로 쓰지 않는다.
- `PriorityTier`: 출처 기준 1~3
- `PriorityReason[]`: 근거 목록 (운영자에게 표시)
- 같은 Tier 안에서는 정렬 키 순서 비교 (연속교육 → 교사 직접강의 → …). 정렬 키 순서는 [미정]
- 신청자 협조도는 주관 점수가 아니라 기록 기반 (서류 제출 지연, 연락 지연, 일정 변경 횟수)

### 4.3 Feasibility [확정: Priority와 분리]
현재 조건에서 실제로 운영 가능한가. 항목: 최소 인원, 강사, 지역, 교구.
결과: FEASIBLE / ADJUSTMENT_REQUIRED / INFEASIBLE [가설].
불가능해도 바로 반려하지 않고 대체 일정을 협의할 수 있다.
[가설] 조회 시 계산하고, 운영자가 확정을 결정한 시점의 결과만 스냅샷으로 남긴다.

## 6. 변경 관리

### 6.1 신청자 변경 권한 [확정]
| 구분 | 항목 |
| --- | --- |
| 즉시 변경 | 담당자 전화번호, 학교 상세정보, 확정 전 희망 교육일 |
| 운영자 승인 후 변경 | 학생 수, 확정 교육일, 교사 직접강의 여부, 교육 취소 |
| 변경 불가 | 프로그램 |

승인 Workflow: Applicant → ChangeRequest → Operator Review → APPROVED / REJECTED. 승인 전에는 EducationClass를 바꾸지 않는다.

[가설] ChangeRequest에 요청 당시 값(또는 Class version)을 저장한다. 승인 시점에 현재 값이 다르면 운영자에게 경고한다.
[가설] 교육이 취소되면 대기 중인 ChangeRequest는 자동 종료한다.

### 6.2 운영자 직접 변경 [확정]
운영자는 ChangeRequest 없이 직접 변경한다. 반드시 기록: 변경 전 값, 변경 후 값, 사유, 변경자, 시각, 요청 채널(PHONE, KAKAO, SYSTEM, ETC).

### 6.3 변경 이력 [가설]
한 번의 업무 변경에서 여러 필드가 바뀔 수 있으므로 `ChangeEvent 1 : N ChangeDetail(field, before, after)`.
운영자 직접 변경과 승인된 ChangeRequest는 모두 같은 경로를 탄다: 변경 적용 → ChangeEvent 저장 → Impact Analysis → Task 생성.

### 6.4 Impact Analysis [확정: 핵심 기능]
| 변경 | 영향 |
| --- | --- |
| 학생 수 | 교구 필요 수량 재검증, 강사 구성 재검증, 간식 수량 변경 |
| 교육일 | 교구 예약 재검증, 강사 일정 재검증, 배송 일정 재검증, 간식 일정 변경, 신청자·담당자 안내 |
| 취소 [가설] | 교구 예약 해제, 강사 배정 취소, 열린 Task 취소, 대기 ChangeRequest 종료, 안내 Task 생성 |

자동 처리 (계산 가능): 교구 가용량, 강사 일정 충돌, 이력 저장, Task 생성.
사람 Task (협의·판단): 강사에게 새 일정 문의, 학교와 대체 일정 협의, 간식 업체 변경 요청, 안내.
강사 자동 재배정은 목표가 아니다 [확정].

## 7. Task와 Readiness

### 7.1 Task [확정 의미]
도메인 변경이나 이벤트 때문에 사람이 추가로 처리해야 하는 운영 업무. 단순 Todo가 아니다.
필드: EducationClass, TaskType, AssigneeRole, AssigneeUser, DueDate, Status, Origin(발생 원인, 예: ChangeEvent id).

[가설] 규칙
- 같은 Class에 같은 TaskType의 열린 Task가 있으면 새로 만들지 않고 내용을 갱신한다 (학생 수 20→25→23).
- 조건이 해소되면 자동 종료되는 Task가 있다 (예: 강사 미배정 Task는 배정 수락 시 종료).
- 모든 상태 변경을 Task로 만들지 않는다. Domain State / Workflow Step / System Action / Human Task를 구분한다.
- 간식, 안내는 MVP에서 도메인 기능이 아니라 Task로만 다룬다.

### 7.2 Readiness [가설: 계산 결과]
항목: 강사, 교구, 사전서류, 간식, 배송, 미처리 Task. 각 READY / WARNING / BLOCKED, Overall은 가장 나쁜 값.
운영자 대시보드는 전체 목록이 아니라 문제 있는 교육(강사 미배정, 교구 부족, 미제출 서류, 배송 확인 필요, 변경 후 미처리 Task)을 먼저 보여준다 [확정].

## 8. 교구

### 8.1 시간 기반 한정 자원 [확정]
교구는 배송 → 교육 → 회수 동안 점유된다. 예: 교육 10/17~18, 배송 10/15, 회수 10/20 → 점유 10/15~10/20.

가용량 = 보유량 − 요청 기간과 겹치는 활성 예약 수량 합계
겹침: `existing.start <= requested.end AND existing.end >= requested.start`

### 8.2 예약 시점 [확정]
- 일정 협의 조건에 교구 가용 확인이 포함되며, 교육 일정이 확정될 때 교구 일정도 함께 확정(예약)한다.
- 실제 택배 발송 같은 물리적 배정은, 교육이 임박했거나 우선순위가 높은 경우 먼저 진행하기도 한다.

[가설] KitReservation 상태: RESERVED(일정 확정) → SHIPPED → RETURNED / RELEASED(취소). 협의 단계에서는 예약 없이 가용량 조회만 한다.
[가설] 배송 리드타임, 회수 기간은 Program 또는 KitType 속성으로 둔다. 회수 지연은 점유 기간을 늘리며 영향 분석 대상이다.
[미정] 교구 파손·분실 처리.

### 8.3 프로그램별 교구 규칙 [확정]
학생 1명당 1개, 2명당 1개, 고정 수량, 교구 없음, 여러 KitType 동시 사용. [가설] `ProgramKitRule(program, kitType, 계산 방식, 값)`.

### 8.4 동시성 [가설: 구현 전략]
같은 교구의 남은 수량을 여러 교육이 동시에 예약할 수 있다 [확정].
- KitType 행을 `SELECT ... FOR UPDATE`로 잠근 뒤 겹치는 예약 합계를 계산하고 insert한다. 겹치는 예약 행만 잠그면 새로 들어오는 예약을 막지 못한다.
- EducationClass 일반 수정은 `@Version` 낙관적 락.
- 동시 요청 테스트(예: 남은 30개에 30개 예약 2건 동시 요청 → 1건만 성공)를 포트폴리오 핵심 테스트로 둔다.

## 9. 강사

### 9.1 구분과 역할 [확정]
학교 교사 직접강의 / 외부 강사(강사 Pool에서 배정).
역할: LEAD, ASSISTANT, SAFETY. 보통 2~3명, 역할별 1명. 주강사·보조강사는 대부분 필수, 안전요원은 일부 교육에서 선택.
- 학교 교사는 어느 학교에든 배정될 수 있다 (소속 이력 불필요).
- 허용 조합 (LEAD, ASSISTANT, SAFETY): (교사,교사,교사) (강사,교사,교사) (강사,교사,강사) (강사,강사,교사) (강사,강사,강사). 즉 LEAD가 교사면 다른 역할도 모두 교사 (2인 운영도 같음).
- 교사 배정 시 추가 업무: 학교장 결재 서류(외부 강의용) 수령(본인 학교·다른 학교 모두), 공문 발송(선택, Task에서 판단하고 기록).
배정 확인: 프로그램 가능 여부, 날짜, 시간, 지역, 기존 배정.

### 9.2 배정 Workflow [확정]
교육 확정 → 배정 담당자 확인 → 후보 강사 연락 → 응답 대기 → 거절 시 다음 후보 → 수락 → 배정 확정.
`InstructorAssignment` 상태: REQUESTED, ACCEPTED, REJECTED, CANCELLED. 배정 변경 이력을 보존한다.
교육일이 바뀌면 기존 강사에게 먼저 가능 여부를 확인하고, 안 되면 새 강사에게 요청한다.

### 9.3 중복 배정 방지 [확정: 같은 날짜 금지]
[가설] 애플리케이션 검사 + DB 제약 이중 방어.
- MVP1(MySQL): ACCEPTED일 때만 날짜 값을 갖는 컬럼(그 외 NULL)을 두고 `(instructor_id, 그 컬럼)` 유니크. MySQL 유니크 인덱스는 NULL 중복을 허용한다.
- MVP2(PostgreSQL): 날짜 기준은 partial unique index, 시간대 기준으로 바뀌면 `btree_gist` + exclusion constraint.
[확정] 같은 날짜에 다른 교육 배정 금지 규칙을 유지한다. 바뀌면 날짜가 아니라 Session 시간 overlap으로 바꾼다.

## 10. 서류

### 10.1 규모 [확정]
기수당 교육 약 40개, 강사 80~100명, 신청자 약 40명, 서류 800~1,000건. 기존에는 운영자가 전부 직접 확인.

### 10.2 종류 [확정, 법적 명칭은 미확정]
- 학교/신청자 사전서류: 사전 안전점검, 피난도, 화재보험 관련
- 외부 강사: 통장사본, 신분증 사본, 정산·내부결재 자료, 범죄경력 조회 동의 관련
- 교사 직접강의: 외부강의 승인·동의, 학교장 승인 관련
- 안전요원: 안전 교육·자격 증빙
- 교육 후 Class 자료: 사진, 영상, 서명부, 사후 안전점검, 결과보고 (강사 Profile이 아니라 EducationClass에 제출)

### 10.3 구조 [확정: 분리]
- `DocumentRequirement`: 누가 무엇을 제출해야 하는가 (역할, 교육 조건에 따라 결정)
- `DocumentSubmission`: 실제 제출 파일. 1차 제출 → 검토 → 재제출 요청 → 2차 제출 → 승인 이력.

### 10.4 개인정보 [미정: 정책 필요]
신분증, 통장사본, 범죄경력 관련 자료가 포함된다. 접근 권한, 접근 로그, 보관·삭제 시점, 저장 방식(비공개 스토리지 + 만료 URL 등)을 정해야 한다. 법적 보관 기간은 확인 전이므로 임의로 정하지 않는다.

## 11. 사용자와 권한 [확정]

내부: 운영자, 교구 담당자, 서류 담당자, 강사 배정 담당자, 관리자(등급 없음, 모든 기능 접근).
외부: 신청자, 강사. 한 사람이 여러 역할을 가질 수 있다 (교사 = APPLICANT + INSTRUCTOR).
방향: User → Role → Permission.

[가설] RBAC만으로는 부족하다. "강사는 자기 Assignment만", "신청자는 자기 교육만"은 소유 관계 검사로 별도 구현한다.

신청자 기능: 사전 신청, 정보 변경, 일정 확인, 교구 배송 조회, 서류 제출, 취소 요청.
강사 기능: 내 일정 조회, 배정 요청 수락·거절, 개인 서류 제출, Class 자료 제출.
셀프서비스 조회: 확정 일정, 학생 수, 교육 상태, 배송 상태·송장, 강사 배정 상태, 필요 서류와 제출 상태, 운영 안내. 챗봇은 범위 밖.

## 12. 규모 [확정]
강사 약 100명, 누적 교육 인원 약 2,400명(설계 목표 4,000명 이상), Class 수백 건, 내부 사용자 10명대.
수만 건에서도 정상 조회되면 충분하다. 핵심 기술 문제는 트래픽이 아니라 여러 사용자가 같은 교육과 제한 자원을 동시에 다룰 때의 데이터 정합성이다.

## 13. 기술 방향

| 항목 | MVP1 | MVP2 |
| --- | --- | --- |
| DB | MySQL (현재 레포) | PostgreSQL 전환 예정 [확정] |
| 마이그레이션 | Flyway | Flyway |
| 테스트 | JUnit, Testcontainers(MySQL) | Testcontainers(PostgreSQL) |
| 후속 업무 유실 방지 | 변경과 Task 생성을 같은 트랜잭션에서 처리 [가설] | 외부 부작용(알림, LMS 반영)이 생기면 Transactional Outbox 검토 |
| 배포 | Docker | AWS |

기술 선택은 도메인 사실보다 우선하지 않는다.

## 14. MVP 범위 [가설: 최대한 빨리 완성하는 것이 목표]

### MVP1: 한 흐름을 끝까지
신청 등록(운영자 직접 입력), 신청자 로그인과 ChangeRequest → 우선순위 정렬 → 교육 확정(Class + Session) → 교구 예약(동시성 처리) → 강사 배정 요청·수락 → 학생 수/교육일 변경(운영자 직접 + 신청자 ChangeRequest) → ChangeEvent + Impact Analysis → Task 생성 → 예외 대시보드 조회 API

완료 기준: 2장의 장애 사례 3개가 인수 테스트로 통과, 교구 동시 예약 테스트 통과, README에 흐름도와 실행법.

### MVP2
PostgreSQL 전환, CSV·LMS import, 서류(Requirement/Submission), LMS 크롤링 어댑터, 중복 신청 후보 탐지, Readiness 고도화, 배포.

### 후순위
간식 시스템, 택배 API, 복잡한 알림, 강사료 정산, 결과보고 고도화, 챗봇.

## 15. 열린 질문 [미정]
- 하나의 신청이 여러 Class로 나뉜 실제 사례가 있는가
- 같은 Tier 안의 정렬 키 순서
- 중복 신청 판별 기준
- 교구 파손·분실 처리
- 서류 보관·삭제 정책
